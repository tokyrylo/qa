OAuth 2.0 — безопасный способ делиться доступом

Что такое OAuth 2.0?

Представь, что ты хочешь дать своему другу доступ в спортзал, чтобы он мог ходить туда вместо тебя, но не хочешь отдавать ему свой ключ от квартиры.

OAuth 2.0 — это как система, которая позволяет тебе выдать «временный пропуск» другу, с ограниченными правами и сроком действия, чтобы он мог пользоваться спортзалом, но не мог заходить в твою квартиру или менять твои вещи.

Как работает OAuth 2.0?

  • Ты (пользователь) хочешь дать приложению (например, новому фитнес-трекеру) доступ к своим данным (например, расписанию в спортзале) без передачи пароля.

  • Приложение перенаправляет тебя на сайт спортзала (сервер авторизации), где ты входишь под своим аккаунтом.

  • После успешного входа сервер выдаёт приложению токен доступа (access token), который даёт право пользоваться твоими данными.

  • Приложение использует этот токен для запросов к API спортзала.

  • Токен ограничен по времени и правам — если он истекает, приложение может получить новый с помощью refresh token или попросить тебя войти заново.

Ключевые роли в OAuth 2.0

  • Resource Owner (Пользователь) — ты, владелец данных.

  • Client (Клиент) — приложение, которому ты даёшь доступ.

  • Authorization Server (Сервер авторизации) — проверяет твою личность и выдаёт токены.

  • Resource Server (Сервер ресурсов) — хранит данные и принимает запросы с токеном.

Почему OAuth 2.0 — это удобно и безопасно?

  • Ты не передаёшь пароль приложению — только токен с ограниченным доступом.

  • Можно легко отзывать доступ (например, отменить выданный токен).

  • Приложения получают минимально необходимый доступ (принцип наименьших привилегий).

💡 Аналогия с рестораном: Ты не даёшь официанту ключ от своего дома, а даёшь ему временный пропуск, который позволяет только заходить в ресторан и заказывать еду, но не менять интерьер или заходить в твою квартиру.

Пример работы OAuth 2.0 — шаг за шагом

Сценарий

Ты — пользователь, хочешь, чтобы фитнес-приложение получило доступ к твоему расписанию спортзала без передачи пароля.

Шаг 1. Клиент запрашивает авторизацию

Фитнес-приложение перенаправляет тебя на страницу авторизации спортзала:

GET https://auth.sportzala.com/authorize?response_type=code&client_id=fitness123&redirect_uri=https://fitnessapp.com/callback&scope=read_schedule

Шаг 2. Пользователь входит и даёт разрешение

Ты вводишь логин и пароль спортзала и подтверждаешь, что фитнес-приложение может читать твоё расписание.

Шаг 3. Сервер авторизации отдаёт код

Если всё успешно, сервер спортзала отправляет приложению временный код:

https://fitnessapp.com/callback?code=abc123

Шаг 4. Клиент меняет код на токен

Фитнес-приложение отправляет код на сервер авторизации:

POST https://auth.sportzala.com/token
Content-Type: application/x-www-form-urlencoded
grant_type=authorization_code&code=abc123&redirect_uri=https://fitnessapp.com/callback&client_id=fitness123&client_secret=secretkey

Шаг 5. Сервер выдаёт access token

Сервер отдаёт фитнес-приложению токен доступа и (опционально) токен обновления:

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "def456"
}

Шаг 6. Клиент использует access token

Теперь фитнес-приложение может запрашивать данные от спортзала, передавая токен:

GET https://api.sportzala.com/schedule
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

Шаг 7. Обновление токена (если access token истёк)

Если access token просрочен, приложение может использовать refresh token, чтобы получить новый токен без вмешательства пользователя.

💡 Аналогия с рестораном: Ты дал другу временный пропуск, чтобы он мог заходить и заказывать в ресторане вместо тебя. Когда срок пропуска истёк, он идёт и получает новый, не прося тебя снова.
