Как проверять ответы API

Когда ты делаешь запрос к API, это как заказать блюдо в ресторане: важно не только то, что официант принёс, но и в каком состоянии он это принёс.

Проверка ответа API — это как контроль качества:

  • правильно ли приготовлено

  • соответствует ли заказу

  • не испортилось ли по дороге

1. Проверяем статус код

Первое, на что стоит смотреть — это HTTP Status Code.

📜 Примеры:

  • 200 OK — всё хорошо, заказ доставлен.

  • 404 Not Found — такого блюда в меню нет.

  • 500 Internal Server Error — на кухне пожар (или повар ошибся).

Как проверить:

В Postman, curl или DevTools смотри первую строчку ответа сервера.

curl -i https://api.example.com/menu

2. Проверяем заголовки ответа

Заголовки — это как заметки от кухни.

📌 На что обратить внимание:

  • Content-Type — формат «блюда» (JSON, HTML, XML и т.д.)

  • Cache-Control — можно ли хранить это блюдо на потом

  • Set-Cookie — сервер запомнил что-то о тебе

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

3. Проверяем тело ответа

Это собственно данные, которые ты получил.

Пример JSON-ответа:

{
  "id": 101,
  "name": "Маргарита",
  "price": 450
}

Что проверить:

  • Все ли поля есть?

  • Правильные ли значения?

  • Правильный формат? (например, цена числом, а не строкой)

4. Проверяем время ответа

В ресторане важно, чтобы еда была горячей, а в API — чтобы ответ пришёл быстро.

  • Обычно хороший API отвечает за 100–500 мс.

  • Если API думает по 5 секунд — что-то не так.

Как проверить:

Postman, curl (-w "%{time_total}") или вкладка Timing в браузере.

5. Проверяем корректность данных

Даже если API ответил 200 OK, это не значит, что данные верные.

Например:

  • Запросил пользователя с id=5, а получил id=7 — значит, перепутали заказ.

  • Цена блюда отрицательная — кто-то явно ошибся.

📝 Чек-лист проверки ответа API

  1. Статус код
  2. [ ] Соответствует ли ожидаемому (200, 201, 400, 404, 500 и т.д.)

  3. [ ] Нет ли неожиданных кодов ошибок

  4. Заголовки ответа

  5. [ ] Content-Type верный (например, application/json для JSON)
  6. [ ] Заголовки безопасности (X-Content-Type-Options, Strict-Transport-Security и др.)

  7. [ ] Cache-Control и Expires настроены правильно

  8. Тело ответа

  9. [ ] Формат соответствует ожидаемому (JSON, XML, HTML)
  10. [ ] Все обязательные поля присутствуют
  11. [ ] Поля содержат корректные типы данных (числа, строки, массивы)
  12. [ ] Значения полей логически верны (цена ≥ 0, даты в правильном диапазоне)

  13. [ ] Нет лишних или тестовых данных

  14. Время ответа

  15. [ ] В пределах нормы для сервиса (обычно < 500 мс)

  16. [ ] Нет задержек при повторных запросах

  17. Корректность данных

  18. [ ] Данные соответствуют запросу (если искали id=5, пришёл именно id=5)
  19. [ ] Данные актуальны (нет устаревшей информации)

  20. [ ] Уникальность там, где она нужна (например, email пользователя)

  21. Кодировка

  22. [ ] Символы не искажены (UTF-8 без ошибок)

  23. [ ] Нет проблем с национальными символами (русский, китайский и т.д.)

  24. Безопасность

  25. [ ] Нет лишней информации об ошибках (стек-трейсы, конфигурация сервера)
  26. [ ] Доступ к данным корректно ограничен (нет чужих данных)
  27. [ ] Нет чувствительных данных в ответе (пароли, токены в открытом виде)
