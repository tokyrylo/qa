📌 Версионирование API

Версионирование API — это практика управления изменениями в API с помощью указания версии, чтобы изменения не ломали работу существующих клиентов.

🔹 Зачем нужно версионирование

  • ✅ Обеспечивает обратную совместимость — старые клиенты продолжают работать.
  • ✅ Позволяет постепенно внедрять новые функции без сбоев.
  • ✅ Упрощает поддержку и отладку разных версий.

🔹 Форматы версионирования

  1. В URL (наиболее распространённый способ) 
https://api.example.com/v1/users
https://api.example.com/v2/users

➡ Плюсы: просто, наглядно.
➡ Минусы: приходится дублировать код.

  1. В заголовках 
GET /users HTTP/1.1
Host: api.example.com
Accept: application/vnd.example.v2+json

➡ Плюсы: URL остаётся чистым.
➡ Минусы: сложнее тестировать вручную.

  1. Через параметры запроса (редко) 
https://api.example.com/users?version=2

➡ Минусы: обычно не рекомендуется, т.к. легко сломать кэширование.

🔹 Роль QA в версионировании API

Что тестировать:

  • [ ] Поддержку нескольких версий API параллельно.
  • [ ] Обратную совместимость:
  • Старые клиенты работают с новой версией API.
  • Новые клиенты могут обращаться к старой версии без ошибок.
  • [ ] Корректность документации — каждая версия должна иметь своё описание.
  • [ ] Актуальность эндпоинтов: устаревшие методы должны быть помечены как deprecated.

🔹 Чеклист для QA

  • [ ] Есть чёткое обозначение версии (в URL, заголовках или параметрах).
  • [ ] При обновлении версии изменения задокументированы.
  • [ ] Старые версии работают до даты их удаления.
  • [ ] Клиенты получают понятную ошибку при обращении к неподдерживаемой версии (например, 410 Gone).
  • [ ] В Swagger / OpenAPI есть отдельные схемы для разных версий.

🔹 Пример для тестирования

Запрос к v1:

GET /api/v1/users HTTP/1.1
Host: localhost:8000

Запрос к v2:

GET /api/v2/users HTTP/1.1
Host: localhost:8000

Проверить:

  • Ответы соответствуют документации каждой версии.

  • Формат JSON одинаковый или описаны изменения.

  • Нет неожиданного изменения полей.

💡 Совет для QA: При тестировании версионирования полезно держать два набора тестов — для текущей и новой версии, чтобы быстро находить несовместимости.

Эндпоинт Версия v1 Версия v2 Изменение / комментарий
/api/v1/users Возвращает id, name, email Возвращает id, full_name, email Поле name заменено на full_name
/api/v1/orders Параметр status (string) Параметр status (enum: pending, done) Добавлена валидация значения
/api/v1/products Пагинация через page, limit Пагинация через offset, limit Изменён способ пагинации
/api/v1/login Возвращает token Возвращает access_token, refresh_token Добавлен refresh-токен
/api/v1/register Поле username обязательное Поле username необязательное Логика регистрации изменена

🔍 Как использовать таблицу

  1. Перед тестированием новой версии — пробежать глазами изменения и составить список тест-кейсов.
  2. При регрессионном тестировании — убедиться, что старое поведение не нарушено (если не указано обратное).
  3. Для автоматизации — можно генерировать тесты на основе этой таблицы, чтобы проверять поля и параметры.

💡 Совет:
Ведение такой таблицы особенно важно в проектах с частыми релизами API — она экономит время и помогает избежать пропуска изменений.

✅ Чеклист проверки обратной совместимости API

1. 📄 Документация и спецификация

  • [ ] Сверить новую версию API с документацией (OpenAPI/Swagger).
  • [ ] Проверить, что устаревшие поля и эндпоинты помечены как deprecated.
  • [ ] Убедиться, что примеры в документации соответствуют реальным ответам сервера.

2. 🔄 Эндпоинты и маршруты

  • [ ] Все существующие эндпоинты старой версии возвращают корректный HTTP-статус.
  • [ ] Если эндпоинт был удалён — есть сообщение об ошибке с указанием новой версии/маршрута.
  • [ ] Нет неожиданных изменений в именах эндпоинтов (например, /users → /user).

3. 📦 Структура данных (JSON Schema)

  • [ ] Все обязательные поля в ответах остались без изменений.
  • [ ] Изменения полей задокументированы (например, name → full_name).
  • [ ] Новые поля не ломают парсинг старых клиентов.
  • [ ] Типы данных не изменились (string → integer и т. д.).

4. ⚙️ Параметры запросов

  • [ ] Все старые параметры запроса поддерживаются.
  • [ ] Значения параметров не изменили допустимый диапазон или формат.
  • [ ] Если параметры были удалены — API возвращает понятную ошибку.

5. 🔐 Авторизация и безопасность

  • [ ] Способ авторизации остался рабочим (Bearer Token, JWT и т. д.).
  • [ ] Нет изменений в формате токена.
  • [ ] При попытке авторизации старым способом возвращается понятная ошибка.

6. 📊 Производительность и лимиты

  • [ ] Лимиты запросов (rate limit) не изменились без предупреждения.
  • [ ] Нет неожиданного роста времени ответа API.
  • [ ] Пагинация работает так же, как в предыдущей версии (если не было изменения в таблице изменений).

7. 🧪 Тестирование на основе таблицы изменений

  • [ ] Пройтись по каждому изменению в таблице и протестировать старое и новое поведение.
  • [ ] Сравнить ответы API с эталонными (Diff-инструментами, например, Postman или JSONDiff).
  • [ ] Зафиксировать несовместимые изменения в баг-трекере.

💡 Совет:
При большом API удобно автоматизировать этот чеклист с помощью Postman Collection Runner или Newman, чтобы проверять старую и новую версию API параллельно.
