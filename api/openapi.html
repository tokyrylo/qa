📄 Документация API в OpenAPI / Swagger (глазами QA)

Swagger (OpenAPI Specification) — это интерактивная документация для API, которая позволяет тестировщику: - быстро понять, какие методы есть в API, - узнать, какие данные они принимают и возвращают, - тестировать API прямо из браузера без Postman или Insomnia.

🎯 Цели QA при работе со Swagger

  1. Проверить полноту документации:
  2. Все ли эндпоинты задокументированы?
  3. Совпадают ли описания с фактическим поведением API?

  4. Есть ли примеры запросов и ответов?

  5. Проверить соответствие спецификации и реализации:

  6. Типы данных (string, integer, boolean) совпадают?
  7. Обязательные поля (required) действительно обязательны?

  8. Описанные коды ошибок реально возвращаются?

  9. Найти несоответствия и баги:

  10. Метод описан как GET, а по факту изменяет данные (нарушение REST).
  11. В описании указано поле, которое сервер не возвращает.
  12. Нет описания для кодов ошибок (400, 401, 500).

🔍 Структура документации Swagger глазами QA

  • Метод и путь (GET /users/{id})
  • Описание — должно объяснять назначение метода.
  • Параметры:
  • Path — обязателен ли id?
  • Query — фильтры, сортировка.
  • Body — формат JSON, обязательные поля.
  • Коды ответов:
  • Указаны ли все возможные (200, 400, 401, 404, 500)?
  • Примеры:
  • Есть ли корректный пример запроса и ответа?

🧪 Чек-лист QA для работы со Swagger UI

  • [ ] Открыть /swagger или /docs и проверить наличие всех методов.
  • [ ] Для каждого метода выполнить тест через Try it out:
  • [ ] Корректный запрос → ожидаемый 2xx ответ.
  • [ ] Некорректные параметры → соответствующий 4xx ответ.
  • [ ] Отсутствие авторизации → 401 Unauthorized.
  • [ ] Сверить схему request/response в Swagger с реальными данными.
  • [ ] Проверить, что примеры в документации рабочие (копируются и дают результат).
  • [ ] Убедиться, что описаны все обязательные параметры.
  • [ ] Проверить, что указаны коды ошибок и их описание.

🧩 Пример работы QA со Swagger UI

Сценарий: тест регистрации пользователя

  1. Открываем метод POST /users/register.
  2. Читаем описание и схему запроса:
   {
     "name": "string",
     "email": "string",
     "password": "string"
   }

  1. Запускаем Try it out → вводим валидные данные.

  2. Проверяем ответ:

  3. Код 201 Created

  4. JSON содержит id, name, email.

  5. Отправляем запрос без email → ожидаем 400 Bad Request.

  6. Сравниваем с описанием в Swagger:

  7. Если ошибка есть, но в документации нет — это баг в документации.

⚠️ Типичные ошибки, которые находит QA через Swagger

  • Несоответствие типов данных (например, id описан как integer, но приходит как string).

  • Нет описания обязательных полей.

  • Отсутствуют коды ошибок в документации.

  • Пример запроса/ответа не соответствует реальному.

  • Эндпоинт работает, но в Swagger его нет.

  • В Swagger указана одна структура JSON, а сервер возвращает другую.
