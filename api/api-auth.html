🔑 Авторизация и получение токена

После регистрации пользователь должен авторизоваться, чтобы получить токен доступа (обычно JWT или Bearer Token). Этот токен используется для работы с защищёнными эндпоинтами API.

📌 Пример запроса авторизации (HTTP)

POST /auth/login HTTP/1.1
Host: localhost:8000/api/v1/login
Content-Type: application/json

{
  "usernane": "test@example.com",
  "password": "Qq!123456"
}

Ответ (успех):

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6Ikp...",
  "token_type": "Bearer"
}

🚀 Авторизация в Postman

  1. Создай новый запрос.

  2. Метод POST.

  3. URL:

https://localhost:8000/api/v1/login
  1. Во вкладке Headers:
Content-Type: application/json
  1. Во вкладке Body выбери raw → JSON и вставь:
{
  "email": "user@example.com",
  "password": "Qq!123456"
}
  1. Нажми Send.

  1. В ответе скопируй access_token — он понадобится для всех защищённых запросов.

Авторизация в Insomnia

  1. Создай новый запрос (New Request).
  2. Метод POST, URL:
https://localhost:8000/api/v1/login
  1. Во вкладке Body выбери JSON:
{
  "email": "user@example.com",
  "password": "Qq!123456"
}

  1. Отправь запрос (Send).

  2. Сохрани токен из поля access_token.

Авторизация в Swagger UI

  1. Найди эндпоинт POST api/v1/login.

  2. Нажми Try it out.

  3. Введи данные:

  4. "username": "user_test"
  5. "password": "Qq!123456"
  6. Нажми Execute.
  7. Скопируй access_token из ответа.

Как использовать токен в защищённых запросах

В Postman или Insomnia:

  • Перейди во вкладку Headers и добавь:
Authorization: Bearer <твой_токен>

В Swagger UI:

  • Найди кнопку Authorize.

  • Вставь токен:

  • Нажми Authorize, теперь Swagger будет подставлять токен автоматически во все защищённые запросы.

💡 Совет QA: При тестировании защищённых запросов обязательно проверяй:

  • Что без токена запрос возвращает 401 Unauthorized.

  • Что с просроченным или неверным токеном приходит 401 или 403.

  • Что с токеном другого пользователя данные /me не утекут.

🧪 Чеклист тестирования защищённых API

1. Авторизация обязательна

  • Отправить запрос без заголовка Authorization → ожидать 401 Unauthorized.
  • Убедиться, что тело ответа содержит информативное сообщение об ошибке (например, "Missing Authorization Header").

2. Валидность токена

  • Использовать случайную строку вместо токена → ожидать 401 Unauthorized.
  • Использовать токен в неверном формате (Token abc вместо Bearer abc) → ожидать 401.
  • Отправить токен с изменённым символом → 401.

3. Срок действия токена

  • Использовать просроченный токен → 401 Unauthorized или 403 Forbidden (зависит от реализации).
  • Проверить, что сервер не принимает токены, выданные более допустимого времени назад.

4. Проверка прав доступа

  • Попробовать токен пользователя с ролью user для эндпоинта, доступного только admin → ожидать 403 Forbidden.
  • Проверить, что токен от одного пользователя не даёт доступ к данным другого (например, /users/{id}/detail).

5. Формат заголовка Authorization

  • Пробел между Bearer и токеном обязателен.
  • Регистр слов не должен влиять (bearer, Bearer).

6. Негативные сценарии

  • Отправить запрос с пустым токеном → 401.
  • Отправить токен в другом заголовке (например, Auth) → 401.
  • Убедиться, что в ответе не утекут внутренние ошибки или stack trace.
