🔒 Проверка ограничений API

Когда ты тестируешь API, важно проверять не только успешные сценарии, но и ограничения, которые накладывает сервер. Это помогает выявить ошибки и баги, которые могут появляться при необычных условиях.

📌 Основные типы ограничений

  1. Ограничения по параметрам запроса
  2. Минимальные/максимальные значения (age >= 18, limit <= 100)
  3. Обязательные и опциональные поля

  4. Формат данных (например, email должен быть валидным)

  5. Ограничения по авторизации

  6. Только авторизованные пользователи могут выполнять определённые действия

  7. Проверка ролей (admin, user, guest)

  8. Ограничения по частоте запросов

  9. Rate limiting: сервер может ограничивать количество запросов в минуту/час

  10. Например: 100 запросов в минуту → при превышении 429 Too Many Requests

  11. Ограничения по объему данных

  12. Максимальный размер тела запроса

  13. Максимальное количество элементов в списках

  14. Ограничения бизнес-логики

  15. Например, нельзя удалить пользователя, если он является единственным администратором
  16. Проверка уникальности email/username

🚀 Как проверять ограничения

1. Параметры запроса

  • Отправь запрос с минимальным, максимальным и неверным значением
  • Ожидаемый результат: сервер возвращает 400 Bad Request с описанием ошибки

Пример запроса (Postman/Insomnia):

POST /api/v1/users
Content-Type: application/json

{
  "username": "a",
  "email": "not-an-email",
  "age": 10
}

Ожидаемый ответ:

{
  "error": "Возраст должен быть >= 18, email неверный"
}

2. Ограничения авторизации

  • Попробуй выполнить запрос без токена или с токеном другого пользователя

  • Ожидаемый результат: 401 Unauthorizedили 403 Forbidden

Пример запроса на защищённый эндпоинт:

GET /api/v1/me
Authorization: Bearer <невалидный_токен>

3. Rate limiting

  • Отправь много запросов подряд к одному эндпоинту

  • Ожидаемый результат: сервер вернёт 429 Too Many Requests

4. Ограничения объема данных

  • Попробуй отправить слишком большой JSON или массив

  • Ожидаемый результат: 413 Payload Too Large или 400 Bad Request

5. Проверка бизнес-логики

  • Выполни сценарии, которые нарушают правила сервиса

  • Например, удалить пользователя с активными заказами

  • Сервер должен вернуть понятное сообщение об ошибке
